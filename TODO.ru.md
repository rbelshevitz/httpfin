# План httpfin

Текущий продукт является диагностическим наблюдателем. Его задача — понятный
отчёт о пути HTTP/TLS и изменениях отпечатка клиента. Правила доступа он не
применяет и клиентов не блокирует.

## Готово

- [x] Рабочие конфигурации Nginx, завершение TLS, `stream ssl_preread`,
  совместимость модуля и Docker-сборка.
- [x] Ограниченное хранилище в памяти и профили настольных, мобильных браузеров
  и WebView.
- [x] Читаемый отчёт с клиентами, изменениями отпечатка, состоянием данных,
  точкой наблюдения, сравнением с baseline и маскированием секретов.
- [x] Раздельные режимы Docker для smoke-тестов и host/systemd для эксплуатации.
- [x] Интеграционные тесты, проверка случайных входов, перезапуска и гонок.
- [x] Документация для эксплуатации и ручной проверки QA.

## Ближайшие задачи

- [ ] Учёт потерь событий: согласовать состояния `получено -> разобрано ->
  сохранено -> отброшено`, вывести их в служебную проверку и описать сверку с
  access log.
- [ ] Проверить надёжность при неверных правах на socket, переполнении datagram
  и медленном Go-приёмнике. Nginx должен продолжать обслуживать запросы.
- [ ] Провести проверку host-развёртывания: права, перезапуск, health check,
  скачивание отчёта и штатная остановка.

## Дальние задачи

- [ ] Необязательная история в SQLite для поиска после перезапуска. По умолчанию
  не включать.
- [ ] Отдельный wire observer или TLS-aware proxy для исходного ClientHello,
  JA3/JA4 и данных HTTP/2 на уровне соединения. Это новый компонент развёртывания,
  а не расширение текущего HTTP-модуля.
- [ ] Прототип отпечатка под MIT: проверить
  [`psanford/tlsfingerprint`](https://github.com/psanford/tlsfingerprint). Библиотека
  оборачивает Go `net.Listener`, читает ClientHello до `tls.Server` и отдаёт
  JA3/JA4 в контекст запроса. Сначала проверить её в прямом HTTPS-режиме Go;
  не ставить перед production-Nginx до проверок сертификатов, задержек,
  HTTP/2, SNI, таймаутов и перезапуска.
- [ ] Вариант прокси под MIT: проверить
  [`mitmproxy`](https://github.com/mitmproxy/mitmproxy) только в отдельной
  тестовой сети. В прозрачном и reverse-режиме он завершает TLS и создаёт
  сертификаты для перехвата, поэтому клиентам нужно доверить его CA. Это
  вариант для лаборатории или QA, а не готовая замена production-edge для
  произвольных публичных клиентов.
- [ ] Не выбирать `elazarl/goproxy` для production без отдельной проверки
  сопровождения и протоколов. Это MIT HTTP-прокси, но по возрасту и области
  применения он скорее запасной прототип, чем основной вариант.
- [ ] Автоматическое обновление профилей и распределённое хранилище.

## Ограничения текущей версии

- HTTP-модуль работает только после завершения TLS. Он не видит passthrough и
  не разбирает исходный ClientHello.
- Unix datagram быстро и неблокирующе передаёт события. Если сборщик остановлен
  или перегружен, событие может потеряться, а запрос клиента всё равно завершится.
- Если нужно учесть каждый запрос, нужен access log. Он даст записи запросов,
  а будущее долговременное хранилище сохранит подробности httpfin.
- Динамический модуль должен быть собран под ту же версию Nginx и ту же libc.
