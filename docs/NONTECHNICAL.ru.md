# Проверка API и httpfin для QA

Этот документ предназначен для API-тестировщика. `httpfin` наблюдает запросы
перед API продукта и создаёт отчёт. Он не меняет ответ приложения и не
блокирует клиентов.

## Что проверяется

Сначала проверяется согласованный сценарий API продукта: метод, путь, статус,
тело ответа и изменение данных. Затем служебные ручки `httpfin` подтверждают,
что запрос был замечен:

- `/healthz` — работает ли сборщик;
- `/api/connections` — дошли ли наблюдения;
- `/api/report` — отчёт для сохранения в результатах теста;
- `/` — интерфейс наблюдений.

```text
клиент -> httpfin / Nginx -> API продукта
                 |
                 +-> наблюдение и отчёт
```

## Успешный результат

- API продукта отвечает ожидаемо;
- новое наблюдение появляется в списке;
- отчёт можно скачать и прочитать;
- в отчёте видны клиент, профиль, доступные признаки, изменения и точка
  наблюдения;
- отсутствующие данные обозначены как `unknown` или `unavailable`.

## Быстрая проверка

1. Открыть `/healthz`. Обычно ожидается статус `204`.
2. Выполнить согласованный запрос к API продукта.
3. Проверить его бизнес-результат.
4. Открыть `/api/connections` и найти время, адрес, метод, путь и статус.
5. Сохранить `/api/report` как `httpfin-report.txt`.

Если запрос есть в access log, но его нет в `httpfin`, это может быть потеря
вспомогательного события Unix datagram. Сам запрос клиента от этого не должен
ломаться.

## Браузеры и устройства

Проверить по одному запросу из доступных групп:

- Chrome или Chromium на компьютере;
- Firefox;
- Edge;
- Safari или другой WebKit-браузер;
- Chrome или другой Chromium на Android;
- Safari на iPhone/iPad;
- встроенный браузер приложения или WebView.

Профиль вроде `Chrome-like`, `Firefox-like`, `Edge-like`, `Safari-like`,
`Chrome Android-like` или `In-App WebView-like` описывает заявленный
User-Agent. Это ориентир, а не доказательство личности клиента.

Повторить один и тот же запрос из двух клиентов и проверить изменения у одного
адреса. Если выбранная точка наблюдения не передаёт признак, ожидается
`unknown`.

## Что искать в отчёте

- сводку клиентов и число запросов;
- последний обнаруженный профиль;
- TLS, SNI и ALPN, если они доступны;
- ClientHello, JA3, JA4 и HTTP/2 только при наличии отдельного наблюдателя;
- изменения признаков между последовательными запросами;
- точку наблюдения и состояние данных;
- отсутствие исходных значений у параметров `token`, `secret`, `password` и
  `api_key`.

Отсутствие JA3/JA4 в обычном Nginx HTTP-сценарии нормально: после завершения
TLS исходный ClientHello уже недоступен HTTP-модулю.

## Режимы TLS

- При завершении TLS на Nginx видны HTTP-данные и доступные поля TLS, но не
  исходный ClientHello.
- При прямом HTTPS на `httpfin` могут появиться SNI и ALPN.
- При `stream ssl_preread` видны признаки маршрутизации TLS, но не URL,
  заголовки и User-Agent.

Это разные точки наблюдения, поэтому набор полей может отличаться.

## После перезапуска и дефект

История текущего процесса хранится в памяти и после перезапуска может исчезнуть.
Сохранённый отчёт и access log нужно приложить к дефекту вместе со временем,
браузером, устройством, кратким описанием запроса и статусом ответа.

Не прикладывать cookies, пароли, токены, полные Authorization-заголовки и
реальные секреты.

## Ограничения

- User-Agent и отпечаток можно подделать;
- отсутствие события в Go не доказывает отсутствие запроса в Nginx;
- SQLite, постоянная история, учёт потерь и настоящий JA3/JA4 пока не входят
  в штатный режим.
