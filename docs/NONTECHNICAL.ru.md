# Проверка API и httpfin для QA

Этот документ предназначен для API-тестировщика и других сотрудников, которым
нужно проверить запрос без знания внутреннего устройства Nginx-модуля.

## Какой API проверяется

Основной объект проверки — API продукта: тот адрес, метод и сценарий, который
дал тестировщику владелец продукта. Например: вход, получение списка, создание
записи или отправка формы. `httpfin` не заменяет этот API и не определяет, был
ли бизнес-результат правильным.

Служебные ручки самого `httpfin` нужны только для проверки наблюдения:

- `/healthz` — отвечает ли сборщик;
- `/api/connections` — дошли ли наблюдения о запросах;
- `/api/report` — сохранить понятный отчёт для разбора;
- `/` — открыть интерфейс наблюдений.

Сначала проверяется результат API продукта, затем по служебным ручкам
проверяется, что этот запрос был замечен и правильно описан.

Схема выглядит так:

```text
клиент → httpfin / Nginx → API продукта
              ├─ отпечаток и признаки клиента
              ├─ отчёт для команды
              └─ при отдельной настройке — сигнал во внешний контур блокировки
```

В штатной конфигурации `httpfin` только наблюдает. В репозитории уже есть
заготовка security-log, фильтра и выключенного jail для Fail2ban, но полная
цепочка для Nginx перед API пока не завершена: текущая политика не выдаёт
`deny`, а Nginx handoff ещё не передаёт антибот-решение в security-log. Поэтому
сейчас нельзя считать автоматическую блокировку через Fail2ban готовой функцией.
После отдельного включения policy-сервиса или WAF такой контур можно будет
подключить явно.

## Что считается успешным результатом

- сервис отвечает на проверку состояния;
- после тестового запроса новое наблюдение появляется в интерфейсе и в API;
- отчёт можно скачать и прочитать без обращения к разработчику;
- в отчёте видны клиент, профиль, изменения отпечатка и сигнал о подозрении на
  бота;
- отсутствие данных обозначено как `unknown` или `unavailable`, а не как
  доказанное несоответствие;
- один подозрительный признак сам по себе не приводит к блокировке клиента.

## Быстрая проверка API продукта

1. Выполнить согласованный сценарий API продукта с корректными данными.
2. Проверить ожидаемый статус, тело ответа и изменение данных продукта.
3. Повторить сценарий с одной ожидаемой ошибкой: например, без обязательного
   поля или с просроченной тестовой авторизацией.
4. Зафиксировать время, метод, путь, браузер или API-клиент и устройство.

Если бизнес-результат неверный, это дефект API продукта, даже если наблюдение
в `httpfin` выглядит нормально. Если бизнес-результат правильный, но запрос
не появился в наблюдениях или отчёт описывает его неправильно, это дефект
интеграции наблюдения.

## Проверка антибот-сценария

Проверять на тестовом API и только на тестовых адресах:

1. Обычный браузер должен получить штатный ответ API и не попасть под
   блокировку.
2. Тестовый автоматизированный клиент с согласованными признаками должен быть
   виден в отчёте как `suspected` или иметь объяснимый `unknown`.
3. Если включён внешний контур блокировки, только явно разрешённое правило
   `deny` должно изменить ответ или временно заблокировать адрес. В текущем
   штатном режиме этот пункт не проверяется: автоматический бан не включён.
4. Браузерный клиент с изменившимся отпечатком не должен блокироваться только
   из-за этого изменения.

Даже строка `decision=deny` ещё не означает автоматический бан: для Fail2ban
отдельно включают jail и его firewall-action. Установка фильтра или проверка
через `fail2ban-regex` бан не включает.

`not_suspected` означает «достаточных признаков не найдено», а не «клиент точно
человек». `suspected` означает «нужна дополнительная проверка», а не
автоматически «запретить».

## Быстрая проверка httpfin

1. Открыть `http://127.0.0.1:8080/healthz`. Ожидается пустой ответ со статусом
   `204`.
2. Открыть `/`. Должна появиться страница наблюдений. Для новой установки
   список может быть пустым — это нормально.
3. Выполнить несколько запросов к API продукта: из обычного браузера, из другого
   браузера и из согласованного API-клиента.
4. Открыть `/api/connections`. В списке должны появиться наблюдения с временем,
   адресом клиента, методом, URL и статусом ответа.
5. Открыть `/api/report` и сохранить ответ как файл. Отчёт должен содержать
   сводку клиентов и отдельные записи наблюдений.

Если список пуст после запроса через Nginx, сначала проверить access log. Передача
в Go является вспомогательным каналом и может потерять событие; это не должно
ломать сам запрос клиента.

## Проверка браузеров

Проверить хотя бы по одному запросу из каждой доступной группы:

- Chrome или Chromium на компьютере;
- Firefox;
- Edge;
- Safari или другой WebKit-браузер, если доступен;
- Chrome на Android или другой мобильный Chromium;
- Safari на iPhone/iPad или другой мобильный WebKit;
- встроенный браузер приложения или WebView, если продукт его использует.

В отчёте профили могут называться `Chrome-like`, `Firefox-like`, `Edge-like`,
`Safari-like`, `Chrome Android-like`, `Edge Android-like`, `Firefox iOS-like`,
`In-App WebView-like` и подобным образом. Название профиля — ориентир по
заявленному User-Agent, а не подтверждение личности браузера.

Проверить также смену клиента: повторить один и тот же запрос из двух браузеров
и убедиться, что в отчёте у одного адреса клиента отображается изменение
доступных признаков. Если признак не передан в выбранной точке наблюдения,
ожидается `unknown`, а не ошибка теста.

## Проверка отчёта

В сохранённом отчёте найти:

- раздел со сводкой клиентов;
- число запросов каждого клиента;
- последний обнаруженный профиль;
- `bot_signal`: `suspected` или `not_suspected`;
- причину и уровень уверенности сигнала;
- изменения TLS, ALPN, ClientHello, JA3, JA4 и HTTP/2, если они доступны;
- точку наблюдения и состояние данных.

Для обычного браузера отсутствие JA3/JA4 в Nginx HTTP-сценарии ожидаемо. Не
нужно считать это ошибкой: настоящий ClientHello доступен только там, где его
отдельно наблюдают до завершения TLS.

## Проверка секретов

Выполнить тестовый запрос с безопасным вымышленным значением в параметрах
`token`, `secret`, `password` или `api_key`. В отчёте должно остаться имя
параметра, но его значение не должно быть показано. Настоящие ключи и пароли
для этого теста использовать нельзя.

## Проверка разных режимов TLS

- При завершении TLS на Nginx должны быть видны HTTP-данные и доступные поля
  TLS, но не исходный ClientHello.
- При прямом HTTPS на `httpfin` должны появляться SNI и ALPN.
- В режиме `stream ssl_preread` видны признаки маршрутизации TLS, но не URL,
  заголовки и User-Agent.

Не считать разницу между этими режимами ошибкой. Это разные точки наблюдения.

## Проверка после перезапуска

Перед перезапуском сохранить отчёт. После перезапуска убедиться, что сервис
снова отвечает на `/healthz`, но прежняя история в памяти может исчезнуть. Это
ожидаемое поведение текущего режима; сохранённый access log и отчёт остаются
источниками для расследования.

## Что приложить к дефекту

- сохранённый `httpfin-report.txt`;
- время проверки и использованный браузер/устройство;
- URL или краткое описание запроса без секретов;
- статус ответа и скриншот страницы, если проблема видна в интерфейсе;
- соответствующий фрагмент access log, если наблюдение не появилось.

Не прикладывать cookies, пароли, токены, полные Authorization-заголовки и
реальные секреты из URL.

## Ограничения, которые не являются дефектом

- User-Agent и отпечаток можно подделать;
- `not_suspected` означает только отсутствие достаточных признаков, а не
  доказательство, что клиент — человек;
- отсутствие события в Go не доказывает отсутствие запроса в Nginx;
- SQLite, постоянная история, счётчики потерь и настоящий JA3/JA4 пока не входят
  в штатный режим.
