# Как использовать httpfin

`httpfin` ставят перед тестовым или рабочим API. Он не заменяет API, не
изменяет запросы и не блокирует клиентов. Его задача — показать, что дошло до
входной точки: HTTP-поля, User-Agent, доступные признаки TLS и результат
обработки запроса.

## Основной сценарий

```text
клиент → Nginx с httpfin → тестируемое API
                    └──→ отчёт httpfin
```

В рекомендуемом режиме Nginx завершает TLS, а модуль передаёт событие в
сборщик Go. После этого:

1. отправьте один и тот же запрос через Nginx;
2. проверьте обычный результат API: статус, тело и изменения данных;
3. откройте `/api/connections` и найдите запрос;
4. сохраните `/api/report` как приложение к тесту или дефекту.

Пример запроса к тестируемому API:

```bash
curl -fsS https://api.example.test/health
curl -fsS https://api.example.test/health \
  -H 'User-Agent: QA-client/1.0'
curl -fsS http://127.0.0.1:8080/api/report > httpfin-report.txt
```

Первые два запроса идут в тестируемое API. Последний обращается к служебному
сборщику `httpfin` и сохраняет его отчёт. Пути `/healthz`, `/api/connections` и
`/api/report` относятся к самому `httpfin`, а не к API продукта.

## Что проверяют разные команды

### DevOps и SRE

После изменения Nginx, TLS, прокси, передачи исходного адреса или upstream сравните запрос
напрямую с запросом через входную точку:

- адрес клиента;
- Host и SNI;
- ALPN и версию HTTP;
- согласованную версию TLS;
- статус ответа;
- наличие события в отчёте и журнале доступа Nginx.

Время обработки и размер ответа берите из журнала доступа Nginx: текущий
Nginx-модуль не передаёт эти поля в `httpfin`.

Так можно найти потерю исходного IP, неверный виртуальный хост, изменение
HTTP/2 на HTTP/1.1 или задержку между входом и приложением.

### API QA

Для каждого важного клиента выполните один и тот же API-тест: браузер,
мобильный браузер, WebView, SDK и обычный HTTP-клиент. В отчёте сравните:

- User-Agent и определённый профиль;
- метод, путь и статус;
- протокол, TLS, SNI и ALPN, если они доступны;
- изменение признаков между последовательными запросами;
- отсутствие секретов в сохранённом отчёте.

Время и размер ответа добавляйте из журнала доступа, если они нужны для
проверки производительности.

Если изменился ответ API, сначала сравните отчёты клиентов. Если изменился
только транспортный признак, это повод проверить обновление браузера, SDK,
прокси или TLS-библиотеки, но не доказательство ошибки клиента.

### Разработчики API и SDK

Если два клиента получают разный результат, направьте их через одну и ту же
точку наблюдения и сопоставьте метод, URL, Host, User-Agent, протокол, TLS,
время, статус и размер ответа. Время и размер берите из журнала доступа или
прямого Go-наблюдения. Это помогает отделить ошибку приложения от различий
клиента, прокси или входного Nginx.

## Как читать отчёт

Отчёт показывает:

- какие клиенты замечены и сколько запросов выполнено;
- последний профиль клиента по User-Agent;
- доступные транспортные признаки;
- что изменилось относительно предыдущего наблюдения того же адреса;
- известен ли эталон и есть ли повод для проверки.

`Unknown`, `unknown` и `unavailable` означают, что признак недоступен. Они не
означают несовпадение. Профиль и User-Agent можно подделать, поэтому отчёт —
диагностическое свидетельство, а не доказательство личности клиента.

## Какой режим выбрать

| Сценарий | Что делает httpfin | Когда применять |
|---|---|---|
| Nginx завершает TLS | Видит HTTP, User-Agent, статус и доступные TLS-поля | Основной сценарий перед API |
| `httpfin` принимает HTTPS напрямую | Сам завершает TLS и видит HTTP, SNI и ALPN | Отладка TLS без Nginx |
| Nginx `stream` с `ssl_preread` | Видит признаки ClientHello для маршрутизации | Только passthrough; HTTP-отчёта нет |

При сквозной передаче TLS (`passthrough`) `httpfin` не видит URL, заголовки, User-Agent и статус
ответа. В обычном HTTP-модуле Nginx исходный ClientHello уже недоступен, поэтому
JA3/JA4 и отпечаток HTTP/2 не появляются автоматически.

## Что не нужно делать

- не считать User-Agent или профиль доказательством браузера;
- не трактовать отсутствие JA3/JA4 как ошибку обычного режима;
- не использовать отчёт как полный журнал запросов: события хранятся в памяти;
- не ожидать, что `httpfin` будет блокировать запросы или управлять firewall;
- не смешивать служебные адреса `httpfin` с адресами тестируемого API.
